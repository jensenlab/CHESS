CHESSDatabase API Reference

CHESSDatabase records every operation on CHESSCore objects in an append-only SQLite ledger and rebuilds any location's state, at any point in history, by replaying it. The Tutorial shows the whole cycle, and the CHESS Databases chapters of the manual cover each part.

The functions most code uses:

  • Setup: create_db and connect_SQLite, and create_indexes! and drop_indexes! for the indexes reconstruction relies on.
  • Committing locations: generate_location, commit_location!, and release_location.
  • Recording operations: upload, and update to amend history.
  • Rebuilding state: reconstruct_location and reconstruct_location!.
  • The ledger itself: get_last_sequence_id, get_sequence_id, and append_ledger/insert_ledger/replace_ledger.

The rest of this page also lists the lower-level upload, reconstruction, caching, and encumbrance functions those build on.

CHESSDatabase.BULK_FRACTION — Constant
BULK_FRACTION

Ref holding the fraction of the ledger above which plan_reconstruction chooses the global path. 0.01, from the benchmark at 200k, 500k and 1M ledger rows: the bulk transfer closure costs about the same for any request while the key-first closure grows with the rows the keys own, and the two cross at 0.5% to 1.5% of the ledger rows for the ancestors (1% to 3% for the descendents). At 0.01 the bulk path is chosen from there on.

CHESSDatabase.location_reconstruction_index — Constant
location_reconstruction_index

Default (empty) value for reconstruct_contents's loc_index accumulator: a map from LocationID to every (SequenceID, Location) snapshot recorded for it during a single reconstruction pass.

This used to be a single DataFrame scanned in full (filter + sort) on every lookup via find_most_recent_location – correct, but with a reconstruction touching N locations across the replay, that meant up to 2N linear scans of a structure that itself grows to ~2N rows, i.e. O(N²) total work. A well fed by a heavily-reused hub location (thousands of transfers touch that hub over a lab's lifetime) turned this into the dominant cost of reconstruction – see the reconstruction scaling benchmark's REPORT.md for the measurement (99.8% of wall time in this bookkeeping, only 0.2% in the SQL query that finds the transfers in the first place). Keying by LocationID up front makes each lookup scan only that one location's own (typically small) history instead of everything ever touched in the whole reconstruction.

Invariant: each location's entry vector is always in non-decreasing SequenceID order. find_most_recent_location relies on this invariant to binary-search each location's vector instead of scanning it – see its docstring. push_location! keeps the invariant itself: an entry older than the last one (a bootstrap of a location at an earlier sequence point, made by a recursive reconstruct_contents after the caller had already recorded a stub for it at its own foot) is inserted at its place, after the entries with the same SequenceID. The usual case, an entry not older than the last, is a plain append.

CHESSDatabase.UnfilledDrawError — Type
UnfilledDrawError(ledger_id,encumbrance_id,source,destination,quantity,available)

A replay of the ledger drew quantity out of the well source, which held only available at that point. destination is missing for a discard. encumbrance_id is the planned transfer being replayed (0 for a recorded one) and ledger_id the ledger entry of the transfer or discard. shortfall gives the amount missing.

CHESSDatabase._reconstruction_transfer — Function
_reconstruction_transfer(donor,recipient,quantity,configuration::String="")

Internal, non-exported helper used only by the ledger-replay simulation below. Returns new (donor,recipient) objects reflecting a transfer of quantity, without mutating the originals — the replay needs to keep both the pre- and post-transfer versions of each well in its own history log (all_locs), so it can't just mutate in place like transfer! does.

This is deepcopy-based like the old public non-mutating transfer (removed — see reconstruct_location/build_location for the actual preview pattern), but it's safe here specifically because src/dest in this context are always standalone reconstruction shells (parent === nothing, no children) built directly by t(loc_id,n) a few lines up — never part of a live connected tree — so deepcopy has nothing extra to copy.

CHESSDatabase.append_ledger — Method
append_ledger()

Add an entry to the end of ledger and return the ID of that entry.

The next sequence ID is read and the row inserted by a single statement, so two writers cannot be given the same sequence ID (which would make the second look like an amendment of the first). Call it inside the transaction that writes the operation, as upload and update do: if the transaction fails, the row is rolled back with it.

CHESSDatabase.audit_ticks — Method
audit_ticks() -> DataFrame

Find the ledger entries that break the rule of simultaneous ticks, so that existing data can be examined before the enforcement is relied on. Run it on a database written before the rule existed.

The rule: a transfer, discard, movement, lock or activity is alone in its tick; reads, environment attributes, instrument settings and observations can share a tick if no two state the same fact (the same location and attribute, instrument and setting, location and component, child, lock, activity or lot of a location).

One row per entry in violation, with the columns LedgerID, SequenceID, Current (whether the entry is the current revision of its slot, so that a violation in a superseded revision can be told from one in force), First, Second (the offending pair, as "Table row id"), Reason, and Operations (how many operations the entry holds). Empty when the database has none. Superseded revisions are included.

source
CHESSDatabase.backfill_observations — Method
backfill_observations()

One-off migration for a database written before observations existed, where some state is known only from a cache (for example a bottle's contents, cached when it was committed). Returns the number of ledger entries added.

Walks every cache in sequence order and compares it with what the ledger alone predicts at that point. Wherever they differ, the cached state is recorded as observations on a new ledger entry inserted right after the cache's, and the caches from there on are repaired. Afterwards every cache can be recomputed from the ledger.

Labware membership is structural rather than recorded, so it stays with the caches: which labware a well (or anything else filling a labware slot) belongs to, and the grid of slots inside a labware.

cache(loc::Location, sequence_id=nothing, time=Dates.now())

CHESSDatabase.commit_location! — Method
commit_location!(loc::Location) -> Location

Commit an uncommitted (!is_committed(loc)) location subtree to the database, preserving its current structure, attributes, lock/active state, and (for Wells) stock contents.

Returns a new, independent, committed Location – loc itself is left unchanged and still uncommitted (location_id/name/kind are immutable fields on every concrete Location subtype, so committing in place is not possible). Use the returned value going forward, the same way reconstruct_location returns an independent object rather than mutating its input.

Already-committed locations embedded in an otherwise-uncommitted subtree are left as-is (reattached, not re-committed) – commit_location! is safe to call on a mixed tree.

Whatever the new locations hold beyond a fresh location's defaults (stock, attributes, lock and activity state, and which location each child sits in) is recorded as observations on a single new ledger entry, so the ledger alone can reconstruct it. The new locations are then cached at that entry.

See also: build_location, release_location, UncommittedLocationError, observe.

CHESSDatabase.connect_SQLite — Method
connect_SQLite(path)

Open the SQLite database at path and make it the database that every CHESSDatabase function reads and writes. SQLite creates the file if it does not exist; use create_db to set up the CHESS tables in a new file. Calling it again switches to a different database.

CHESSDatabase.create_indexes! — Method
create_indexes!(; progress=true) -> Vector{String}

Create the indexes that make reconstruction cost depend on a location's own history instead of the size of the ledger, on the connected database, and return the names of the ones created. An index is skipped when the table or a column is missing, or when an index with the same leading columns already exists (for example one made by another tool). CHESSDatabase.find_most_recent_location — Method
find_most_recent_location(index, location_id, sequence_id)

Return the most recently pushed Location for location_id with SequenceID <= sequence_id, or nothing if none qualifies. Relies on the same sortedness invariant as the 2-arg method: since entries are always appended in non-decreasing SequenceID order, a binary search (searchsortedlast) finds the rightmost qualifying entry in O(log k) instead of a linear scan. Ties (more than one entry at the same sequence_id) resolve to the last one pushed, matching the insertion-order tie-breaking a linear max-scan would produce.

get_transfer_ancestors(locs::Vector{<:Integer},starting::Integer=0,ending::Integer=get_last_sequence_id(),time::DateTime=Dates.now();encumbrances=false)

Find every transfer relevant to reconstructing locs' contents between starting and ending sequence points.

The result has a Core column (1/0). Core=1 rows are the genuine ancestor closure: locs themselves plus every location transitively feeding them (found by following Source = <already-found Source>.Destination). Core=0 ("collateral") rows are other outgoing transfers or discards of a Core=1 location, to a destination that never itself feeds back into the closure – needed so replay can correctly account for stock a core location sent away to something reconstruct_contents doesn't otherwise care about. Collateral destinations never need their own correct reconstruction – reconstruct_contents bootstraps them as bare Empty() stubs instead of recursing.

The columns are LedgerID, Source, Destination (missing for a discard), Quantity, Unit, Core and SequenceID, one row per ledger entry, ordered by SequenceID.

The closure is walked well by well through the indexes on Transfers and Discards, so the time depends on the transfers of the wells in the closure and not on the length of the ledger. A well that fed many others (a shared reservoir) contributes all of its transfers as collateral. The original whole-ledger query is used for encumbrances=true, and when reconstruction_mode[] is :legacy. For more than LOCAL_KEY_LIMIT locations that own a large part of the ledger the bulk path of plan_reconstruction is used.

With encumbrances=true a protocol counts as enforced by its latest enforcement entry up to enforced_through (default ending), whether or not that entry lies inside starting..ending. A replay that starts from a cache and a bootstrap of an ancestor at an earlier point pass the sequence point being reconstructed, so both see the same protocols as enforced.

CHESSDatabase.reconstruct_history — Method
reconstruct_history(location_id::Integer, facet; from=0, to=get_last_sequence_id(), time=Dates.now(),
                    effective=nothing, order=:asc, limit=nothing, after=nothing, collapse=true, encumbrances=false) -> DataFrame

The history of one facet of a location: the rows at which its value changed between the slots from and to, as recorded by the ledger as of time.

facet is an attribute kind or its name (attr"Temperature", :Temperature), :parent (the id of the parent, missing for none), :locked, :active, :lot (supplier, catalog number and lot of the lot observed on the labware), (:setting, name) (an instrument setting, location_id being the instrument) or a read kind (the reads of that kind, by the time of the read) or :contents (the stock of a well; Value is the Stock, Unit is missing, Origin the well, and Event is transfer in, transfer out, discard, observe_components or cache).

The columns are SequenceID, LedgerID, Time (of the ledger row; of the read for a read kind), Value, Unit, Origin and Event. Origin is the location whose value this is: the location itself, or for an effective attribute the ancestor it was inherited from. Event names the operation (set_attribute, observe_attribute, move, observe_parent, set_lock, observe_lock, set_activity, observe_activity, observe_lot, set_instrument_setting, read), or cache where a cache snapshot gives the value; for an effective attribute it is the event that changed the value, which can be a move.

The value at a slot s is the Value of the last row with SequenceID <= s (history_value_at); no such row means the facet has not been set (a default applies). The first row is the state in force at from, with the slot of the event that last set it, which can lie before from. For a read kind the rows are the reads, ordered by the time of the read.

Keyword Arguments

  1. from, to: the slots; to defaults to the last one.
  2. time: only operations recorded at or before time count, as in reconstruct_location.
  3. effective: for an attribute, true (the default) gives the value the location actually had, taken from the nearest ancestor-or-self whose own value was not missing; false gives only the events recorded on the location itself. Other facets have no effective form and only accept false.
  4. order: :asc (oldest first, the default) or :desc.
  5. limit, after: a page of at most limit rows. after is the SequenceID of the last row of the previous page (for a read kind, its Time); the page holds the rows after it in the chosen order. Only the part of the history a page needs is read.
  6. collapse: with true (the default) a row is kept only if its Value, Unit or Origin differs from the row before it. false keeps every event and cache row of an own facet (an effective history is always collapsed).
  7. encumbrances: with true the history includes the planned (encumbered) operations of the enforced protocols, as the reconstruct_* functions do with encumbrances=true. A planned operation takes effect at the slot of the ledger entry that enforces its protocol, and it hides every real change to the same key after that, as in the reconstruction. Rows it produces have an Event starting with planned. Reads, lots and instrument settings have no planned operations. See docs/history.md.
  8. max_closure: for :contents, throw an ArgumentError when the transfer ancestry of the well has more rows than this.

The value at every slot equals the value of the matching reconstruct_* at that slot and time.

CHESSDatabase.trace_contents — Function
trace_contents(location_id::Integer, sequence_id=get_last_sequence_id(), time=Dates.now()) -> DataFrame

The trace follows the transfers into the well and the observations of its ancestors, with each transfer taking the same fraction of every lot's share of a component as of the component itself. A component observed in a well that held none of it comes from the Lot of the well's labware as of sequence_id, which is how a bottle's contents are attributed to the bottle's lot. The trace is computed from the ledger each time and is not stored. See also trace_cost.

CHESSDatabase.trace_forward — Function
trace_forward(location_id::Integer, sequence_id=get_last_sequence_id(), time=Dates.now(); from_sequence=0) -> DataFrame
trace_forward(lot::Lot, sequence_id=get_last_sequence_id(), time=Dates.now()) -> DataFrame

Find every well that received material from a well, or from the labware received as a lot, as of sequence_id and time. This is the reverse of trace_contents, which finds the lots a well's material came from. It is the list to check when a lot turns out to be bad, or when a transfer is corrected with update.

The result has one row for each well reached, including the starting wells, ordered by when they were first reached, with columns:

  • WellID: the well.
  • ContainerID: the labware the well belongs to (see well_container), or missing if it is not recorded.
  • FirstSequenceID: the sequence ID of the first transfer that brought material into the well, or of the start for a starting well.
  • FirstLedgerID: the ledger entry of that transfer, or missing for a starting well.
  • Depth: the number of transfers between the starting well and this one along that first path.
  • ViaWell: the well that transfer came from, or missing for a starting well. Following ViaWell rebuilds the path.

The trace follows the transfers in the order they happened. A transfer out of a well carries the material on only if it comes after the material arrived, so a transfer out of a well before it received anything is not followed. from_sequence starts a well trace at a later point in the history. A lot starts from every well of the labware that has the lot as of sequence_id, from the beginning of the history.

The trace follows transfers only. It is slightly larger than the exact set: a transfer carries the material on even if an observation has since overwritten that component in the well, and a discard is not a way out. Planned operations (encumbrances) are not followed. The trace is computed from the ledger each time and is not stored.

See also: forward_containers, forward_runs.

CHESSDatabase.update — Method
update(fun::Function, args...; replace=nothing, insert=nothing, time=Dates.now(), instrument=nothing, instrument_time=nothing) -> Integer

Run an operation and record it at a chosen point in the ledger, then validate the result and repair any caches it invalidates. Returns the ledger ID the operation was written to.

update works like upload, but is meant for amending history:

  • replace=s records a new revision of the entry at sequence ID s (see replace_ledger). The replacement must be the same kind of operation as the entry it replaces, otherwise an error is thrown. A slot that holds several operations (see upload_tick) is refused: a replacement of one operation would drop the others, so use update_tick with the complete set.
  • insert=s adds a new entry at sequence ID s, moving later entries back by one (see insert_ledger).
  • With neither, the operation is appended at the end of the ledger.

The ledger row, the operation, validation, and cache repair all happen in one SQL transaction, so if any step fails the database is left exactly as it was. fun is also applied to the in-memory objects in args, as with upload, and that change is not undone on failure; reconstruct from the database to see the recorded state.

ledger_id= is still accepted in place of replace/insert, for a ledger row allocated beforehand, but a row allocated that way is not rolled back if update fails.

See also: replace_ledger, insert_ledger.

Examples

update(transfer!, well_a, well_b, 1u"g"; replace=54)

CHESSDatabase.update_tick — Method
update_tick(operations...; replace=nothing, insert=nothing, time=Dates.now(), instrument=nothing, instrument_time=nothing) -> Integer

Record the complete set of operations of a tick at a chosen point in the ledger, then validate the result and repair the caches it invalidates, as update does for one operation.

  • replace=s records a new revision of the entry at sequence ID s. The operations given are the whole of the new revision: an operation of the old revision that is not repeated is dropped, so a replacement has to state every operation it keeps.
