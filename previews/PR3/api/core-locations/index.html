Locations & Operations

Location types, LocationKinds, occupancy, and the operations that change where things are and what state they are in. See the Locations and Movement & Occupancy manual chapters.

CHESSCore.LocationKind — Type
struct LocationKind

LocationKind is a named, interned, immutable value describing a kind of location or labware (e.g. :Room, :Incubator, :WP96, :AltemisBox, :Well200). It replaces minting a new concrete Julia type per kind — every Location/Labware/Well instance carries a reference to a shared LocationKind value rather than duplicating its descriptive data.

Fields:

  • name: the kind's unique identifier.
  • categories: flat, ordered tags used for occupancy-rule resolution (no chaining/hierarchy).
  • shape: grid shape (rows, cols) if this kind is Labware-like; nothing otherwise.
  • socket: the LocationKind name filling each grid slot, if shape is set.
  • capacity: well volume capacity if this kind is Well-like; nothing otherwise.
  • vendor/catalog: descriptive product data, if applicable.
  • default_parent_cost/default_child_cost: fallback occupancy costs used when no specific or category-based occupancy_cost rule applies.
  • actuatable_attributes: names of AttributeKinds this kind is associated with as an instrument – descriptive only, not enforced; empty for non-instrument kinds.
  • performable_operations: mutating operation functions (e.g. move_into!, transfer!, set_attribute!) this kind's instrument can perform on other locations; empty for non-instrument kinds.
  • readable_types: names of ReadKinds this kind's instrument can produce; empty for non-instrument kinds.
  • is_instrument: whether this kind is capability-bearing (see is_capable) – independent of its structural concretetype, which is decided purely by capacity/shape. A kind can be both capability-bearing and grid-shaped (e.g. a plate reader with a physical deck), in which case it concretizes as Labware with capability data layered on top.

See also: concretetype, @location_kind, @loc_str

CHESSCore.@loc_str — Macro
@loc_str(kind)

String macro to recall a LocationKind registered with @location_kind by name, mirroring @chem_str/@org_str (and sharing their lookup machinery).

loc"WP96" is a pure lookup — it never allocates a new physical instance or touches the database. Actual instantiation stays an explicit call, e.g. generate_location(loc"WP96", "Plate 1").

Example:

julia> loc"WP96"
LocationKind(WP96)

CHESSCore.@location_kind — Macro
@location_kind labsymb categories shape socket capacity vendor catalog [default_parent_cost] [default_child_cost]

Define a new LocationKind and register it under labsymb, both as a const binding (so it can be used directly, e.g. WP96) and in the location_kinds registry (so it can be looked up by name, e.g. for database reconstruction).

Example:

julia> @location_kind WP96 [:Plate] (8,12) :Well200 nothing "Thermo" "123456"
WP96

CHESSCore.GenericLocation — Type
mutable struct GenericLocation <: Location

The concrete Location subtype for locations with mutable, heterogeneous membership over time (rooms, incubators, drawers, ...) — as opposed to Labware (fixed grid) or Well (terminal leaf). Every distinct kind (:Room, :Incubator, ...) is a LocationKind value carried in kind, not a distinct Julia type.

CHESSCore.Location — Type
abstract type Location end

Locations represent the physical objects that make up the lab. Location objects use the AbstractTrees.jl interface to construct relational hierarchies.

The concrete subtypes are GenericLocation (mutable membership over time), Labware (fixed, permanent grid membership), and Well (terminal leaf holding a Stock). Every distinct kind of location/labware (:Room, :Incubator, :WP96, ...) is data (a LocationKind), not a distinct Julia type — see @location_kind.

CHESSCore.occupancy_cost — Method
occupancy_cost(parent::Location,child::Location)

Returns a Rational representing the fractional occupancy of child in parent.

Resolution precedence: an exact (parent kind, child kind) rule (see set_occupancy_cost!) wins outright; otherwise, a single matching category-based rule applies; if more than one category-based rule matches with no exact rule to disambiguate, throws AmbiguousOccupancyRuleError; otherwise falls back to max(parent_cost(parent),child_cost(child)).

CHESSCore.set_occupancy_cost! — Method

CHESSCore.Labware — Type
mutable struct Labware <: Location

The concrete Location subtype for a manufactured physical item with a fixed, homogeneous grid of slots (kind.shape), populated once at creation by build_location and never restructured afterward — add_to!/remove! on a Labware throw FixedMembershipError. CHESSCore.Well — Type
mutable struct Well <: Location

Wells are special Location subtypes that contain a single Stock object.

A well's LocationKind (kind) determines its volume capacity in kind.capacity. kind is a required, explicit constructor argument (not derived from the parent), so a well's capacity is known immediately at construction, whether or not it has a parent yet.

Wells are only allowed to be located in Labware objects and cannot be moved from the labware — they are physically fused to it.

CHESSCore.withdraw! — Method
withdraw!(donor::Well, quant::Union{Unitful.Volume,Unitful.Mass}) -> (Stock, Real)

Remove quant of donor's stock and return it along with its share of the well's cost.

The withdrawn Stock is a proportional slice of the well's contents: withdrawing a quarter of the total quantity takes a quarter of every reagent and organism. The well's cost is reduced by the same fraction, and that amount is returned as the second value. quant must have the same dimension (volume or mass) as the well's total quantity, otherwise an error is thrown.

See also: deposit!, transfer!.

CHESSCore.build_location — Function
build_location(kind::LocationKind,name::String=string(UUIDs.uuid4()),child_namer::Vararg{Function}=plate_namer)

Build a kind Location entirely in memory — no database calls are made, and location_id is nothing (see is_committed). This is the default, ordinary way to get a Location: a plain in-memory Julia object, nothing exceptional about it. Useful for reasoning about hypothetical arrangements without minting real database rows, and it's the building block CHESSCore's own tests and fixtures use throughout. A location built this way cannot be passed to upload/cache (CHESSDatabase) until it's committed — see UncommittedLocationError. To commit a subtree to a database, see commit_location! (CHESSDatabase); to strip a committed location back down to an uncommitted one (e.g. to merge subtrees from separate databases), see release_location (CHESSDatabase).

Previewing hypothetical arrangements: since nothing here is ever committed unless you choose to, this is already the preview mechanism for anything that doesn't exist yet — build it, mutate it freely (move_into!, drain!, lock!, ...), inspect it, and simply never call upload/cache if you decide not to keep it. There's no "restore" step, because nothing was ever committed. For previewing a change to an already-committed location instead, see reconstruct_location (CHESSDatabase).

See also: generate_location, reconstruct_location, commit_location!, release_location (all CHESSDatabase).

CHESSCore._check_capability — Method
_check_capability(instrument::Union{Location,Nothing}, fun::Function)

Shared gate for the four operations whose CHESS Database tables carry an InstrumentID (move_into!/transfer!/set_attribute!/record_read!): if instrument is given, it must have fun in its performable_operations, or this throws ArgumentError. A no-op if instrument is nothing (the default everywhere it's used) – this never mutates instrument and never changes the mutation logic of the operation itself, it only validates.

Checks only the coarse "can this instrument perform this operation at all" axis – actuatable_attributes/readable_types (the finer, per-argument axes) are deliberately not consulted here; they remain descriptive LocationKind data for a possible future planning/scheduling feature.

CHESSCore.can_move_into — Method
can_move_into(parent::Location,child::Location)

returns true if child can be moved into parent, throw an error if not

there are four errors that prevent movement

  1. LockedLocationError: child is locked in its current parent.
  2. AlreadyLocatedInError: child is already located in parent
  3. OccupancyError: parent has occupancy constraints that prevent it from containing child. This could happen if parent is full or if child is never meant to be able to fit inside parent.
  4. FixedMembershipError: child is a Well – wells are physically fused to their labware and can never be independently relocated, regardless of any occupancy rule (see the can_move_into(::Location,child::Well) method below).

See also: move_into!

CHESSCore.observe! — Method
observe!(well::Well, component::StockComponent, quant; instrument=nothing)
observe!(loc::Location, attribute::Attribute; instrument=nothing)
observe!(child::Location, parent::Union{Location,Nothing}; instrument=nothing)
observe!(loc::Location, facet::Symbol, value; instrument=nothing)

Declare one fact about loc as ground truth, whatever history predicted. Unlike the other operations, an observation makes no claim about how the state came about. It only states what the state is.

  • Component: component is present in well at exactly quant, and every other component is unchanged. observe!(well, rgt"glucose", 2u"g"). A zero quant asserts absence. Cost is unchanged.
  • Attribute: loc's own attribute is attribute, as with set_attribute!. A missing value means loc has no local value and defers to its parent.
  • Parent: child is located in parent (or nowhere, for nothing). This moves child like move_into! but ignores child's lock. Occupancy rules still apply.
  • Scalar facets: facet is one of :cost (a Well's cost), :locked or :active.

See _check_capability for instrument.
